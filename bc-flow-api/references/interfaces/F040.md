# F040 Create an eSIM order

The external sales channel calls the Flow platform to create an eSIM order.

Operation: write; distribution documentation: listed.

## Backend behavior

Synchronously creates the local sales/eSIM order. subOrderList must contain exactly one object; number is the card quantity. Provide planSkuCopies or days. ESIMCARD multi-quantity KDDI/SKT paths record a task for asynchronous procurement; ordinary paths also typically await later QR delivery callbacks. F042 queries profile status only, not QR codes. The documented F APIs have no general QR retrieval endpoint; do not invent one or deploy a callback receiver for the user.

Call chain: `SaleController.dispatchRequest` → `SaleOrderApiService.createOrderHandle`.
Source: `flow@93d717b36c/manage-api/src/main/java/com/op/flow/manage/api/service/SaleOrderApiService.java:137`; see [Protocol and environments](../protocol.md) for test-branch differences.

## Response

| Field | Type | Required in docs | Description |
|---|---|---|---|
| `tradeCode` | String | Y | Result code: 1000-success; all other codes-failure |
| `tradeMsg` | String | Y | Interactive result description |
| `tradeData` | Object | N | Definitions are shown in the table below |

### tradeData

| Field | Type | Required in docs | Description |
|---|---|---|---|
| `orderId` | String | Y | Main order ID of flow platform |
| `channelOrderId` | String | Y | Main order ID of sales channel |
| `subOrderList` | Array | Y | Sub-order information |
| `subOrderList[].subOrderId` | String | Y | Sub-order ID of flow platform |
| `subOrderList[].channelSubOrderId` | String | Y | Main and sub-order ID of channel |
| `pickupCode` | String | N | Conditional pickup code from the order claimCode or first suborder claimCode; not a general QR/activation code field |
| `successFlag` | String | N | Some paths return the string "true" when ordering has succeeded; this does not mean a QR code or email has been delivered |

`pickupCode` is conditional on the business path, code availability and response setting; it is not required. Do not treat it as a QR code or expose it unnecessarily in logs/shared reports. The common response builder emits `successFlag` only when true; absence is not failure and must not trigger another order. Judge API success using HTTP 200 and `tradeCode=1000`, then verify final delivery separately.

### Delivery and follow-up queries

Normally reuse the channel's existing N009 notification setup. The Skill neither sends N callbacks nor requires notification reconfiguration for every order. If the user chooses email delivery, use the confirmed address in optional F040 `email`; call F041 to resend only on explicit request. After creation, report the order ID and "Accepted; delivery awaits notification/verification." API success does not prove email delivery.

The 33 F APIs contain no general QR retrieval endpoint; F042 only queries profile status. If the user requests a QR code and this session has no delivery result, briefly explain that it comes through existing notifications or email. Raise a missing delivery integration only when it actually applies; do not make building a callback receiver a prerequisite for all orders. See [F002](F002.md) / [F003](F003.md) for product eligibility and quote selection.
