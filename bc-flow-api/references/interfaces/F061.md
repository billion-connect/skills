# F061 Create a data booster order

The channel adds a data booster to an activated original plan without changing the original plan. Rules: (1) One invocation targets one full ICCID belonging to the original order; an order may contain several cards and the selected card's plan must be activated. (2) Booster and original plan types must match: total-volume with total-volume, daily with daily. (3) Data boosters and booster-acceleration orders are mutually exclusive for the same original order and ICCID. (4) Total-volume plans (planType=2) support only remaining-period boosters; stackDataType may be omitted and defaults to 2. (5) Daily plans require stackDataType.

Operation: write; distribution documentation: not listed (this alone does not prove the backend cannot support it).

## Backend behavior

Creates a data booster order and requires originalOrderId/skuId. Use a stable channelOrderId as the recommended idempotency identifier; the client requires it for write traceability. stackDataType selects booster scope. tradeCode=1000 is returned only when the backend order state is successful, with orderId/channelOrderId. Failures use tradeCode/tradeMsg; do not rely on legacy result/failReason fields.

Call chain: `SaleController.dispatchRequest` → `SaleApiService.createBoosterPackageOrderHandle`.
Source: `flow@93d717b36c/manage-api/src/main/java/com/op/flow/manage/api/service/SaleApiService.java:6324`; see [Protocol and environments](../protocol.md) for test-branch differences.
