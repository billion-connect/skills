# F017 Apply for after-sales service

The sales channel can obtain the list of commodities it can sell, with external sales channel application system as the calling party , And the sales channel submit the after sale apply

Operation: write; distribution documentation: not listed (this alone does not prove the backend cannot support it).

## Backend behavior

Creates an after-sales request through afterSaleService.applyAfterSaleHandle; it does not immediately refund money. Reason codes come from business configuration; do not invent them. Channel/product rules determine requirements for iccid or number, card return and refund amount. In addition to the API after-sales allowlist, the reviewed test branch checks the channel's after-sales switch. Verify review/refund status with F020.

The refund method depends on the reason. For an ordinary channel using `29` (cancel before eSIM download), use automatically calculated `refundType=0`; an agreed amount with `refundType=1` is rejected as `1108 / Invalid refund method`. Reason `20` normally also requires automatic calculation. Do not change the reason to one that contradicts the facts to obtain an agreed refund; channel exceptions depend on platform configuration. Automatic calculation does not need a manually supplied refund amount; verify the actual amount/status using F020.

The API also restricts after-sales reasons independently: ordinary-channel eSIM/eSIM Air orders allow only `29`, other orders only `20`; mismatches return `1107 / Invalid after-sales reason`. Other reasons are checked against the dictionary/order type only when the platform has granted the channel an extended-reason exception (reviewed backend `caseId=12`). API after-sales permission `caseId=29` and extended-reason permission are separate; one does not imply the other. The Skill does not change these settings.

`reason=21` (other reason) applies only to channels/orders with extended-reason authorization and matching business facts; describe the actual reason in `comment`. Automatic or agreed refunds may be supported, but agreed amounts cannot exceed the refundable amount. Without this authorization, do not use 21 to manufacture a pending-review test case. Reasons `20/29` may be approved automatically, so never assume a submitted request can still be changed or cancelled; read back F020. Do not alter existing review status just to test modification/cancellation.

Call chain: `SaleController.dispatchRequest` → `SaleApiService.applyAfterSale`.
Source: `flow@93d717b36c/manage-api/src/main/java/com/op/flow/manage/api/service/SaleApiService.java:4410`; see [Protocol and environments](../protocol.md) for test-branch differences.

## Request parameters

These tables preserve the published field contract. Conditional requirements follow the field descriptions and backend notes above. The client performs partial structural validation; the server still validates product eligibility, permissions, inventory and balance.

|---|---|---|---|
| `tradeType` | String | Y | F017-Apply for after-sales service |
| `tradeTime` | String | Y | Communication time stamp |
| `tradeData` | Object | Y | Definitions are shown in the table below |

### tradeData

| Field | Type | Required in docs | Description |
|---|---|---|---|
| `channelOrderId` | String | Y | Main order ID of sales channel |
| `channelSubOrderId` | String | Y | Main and sub-order ID of channel |
| `reason` | String | Y | After-sales reason code: 20-cancellation without a reason; 29-cancellation before eSIM download |
| `iccid` | Array | Y | Affected ICCIDs |
| `unSubscribeFlow` | String | N | Cancel data plan: 0-no; 1-yes. Must be 1 for eSIM, card and top-up orders. |
| `receivingState` | String | N | Receipt status: 0-not received; 1-received. Required for eSIM and card orders; use 1 for eSIM, actual receipt status for card orders. Omit for top-up orders. |
| `returnCardOrNot` | String | N | Card return: 0-not required; 1-required. Required for eSIM and card orders; use 0 for eSIM, actual return requirements for card orders. Omit for top-up orders. |
| `logisticsNoPerson` | String | N | Person entering the tracking number: 0-customer; 1-warehouse operator |
| `logisticsId` | String | N | Logistics ID |
| `refundType` | String | Y | Refund method: 0-automatically calculated; 1-agreed amount |
| `refundAmount` | String | N | Refund Amount |
| `comment` | String | N | Remarks |
